# bump-dep

Use this skill when the user asks to change a dependency in torch-env:

- **add** ("add `einops` to the env")
- **remove** ("drop `aim`", "get rid of `pysr`")
- **upgrade / bump** ("bump torch", "pick up the latest polars")
- **swap / replace** ("swap `aim` for `mlflow`")

## Mental model

- `environment.linux.yaml` and `environment.mac.yaml` are the **loose specs**
  edited by hand. The pip section is the "main list".
- `lockfiles/requirements.{linux,mac}.txt` are regenerated by CI — never edit
  them locally.
- Adding/removing/renaming/repinning a main-list package is a code change.
  Resolving versions, rebuilding, and tagging are CI's job.
- Releases are tagged `YYYY.MM.N`. CI bumps `N` automatically when the
  main-list changed (add/remove) or when a main-list package resolved to a
  different version on either platform.

## Procedure

You are authorized to run `git add`, `git commit`, `git push`, and
`gh workflow run` without asking, provided the steps below succeed cleanly.
Stop and ask if anything is unexpected (dirty tree, conflicts, failing
preflight, ambiguous package name, package not present when asked to remove).

### 1. Preflight

From `repos/torch-env`:

```bash
git status --porcelain
git rev-parse --abbrev-ref HEAD
```

- Working tree must be clean.
- Branch must be `main` (unless the user said otherwise).
- If unclean or off-main, stop and ask.

For removes/upgrades, also confirm the package is actually present in the
yamls before editing — `grep -n '^\s*- <pkg>' environment.*.yaml`. If absent,
stop and ask.

### 2. Edit both yamls

Both `environment.linux.yaml` and `environment.mac.yaml` have a `pip:` block
that is **alphabetically sorted, case-insensitive**. Mirror the change on both
files unless the user explicitly says it's platform-specific.

- **Add**: insert the package name at the right alphabetical slot.
- **Remove**: delete the line in both files.
- **Swap**: delete the old name, insert the new one at the right slot.
- **Upgrade**: these are loose pins — most entries are bare names. To force
  a floor, change the line to `pkg>=X`. To force an exact version
  temporarily (e.g. avoid a known-broken release), use `pkg==X` and add a
  comment on the next line explaining why. Otherwise, for a bare-name
  package, no edit is needed — CI re-resolves on every run.
- Preserve existing formatting (2-space indent, leading `- `, no quotes
  unless they were already there).
- Do not touch the conda section, the `--extra-index-url` line, or unrelated
  comments.

If a package name differs between PyPI and import name, use the PyPI name
(that's what pip resolves).

### 3. Commit

Follow the existing commit-message style. Look at `git log --oneline -20`
for examples; the recent convention is:

- `feat: add <pkg> to shared env`
- `feat: promote <pkg> from <repo>` (when promoting a consumer-repo dep)
- `fix: swap <old> for <new> (<reason>)`
- `chore: drop <pkg>`
- `chore: bump <pkg> floor to >=X` (for explicit version-pin changes)

Use `feat:` for additions, `fix:` for swaps/replacements driven by a bug,
`chore:` for removals and pin-only edits. Keep the subject under ~70 chars.
A body is optional but useful when the change is non-obvious (e.g. why a
wheel isn't available — see `f52edad` for the aim→mlflow precedent).

Stage only the yaml files explicitly:

```bash
git add environment.linux.yaml environment.mac.yaml
git commit -m "$(cat <<'EOF'
<subject>

<optional body>

Co-Authored-By: Claude Opus 4.7 (1M context) <noreply@anthropic.com>
EOF
)"
```

Do **not** `git add -A` (avoids picking up stray files). Do **not** stage
lockfiles.

### 4. Push

```bash
git push
```

If the push is rejected (remote ahead), stop and ask — don't force.

### 5. Trigger the release workflow

```bash
gh workflow run monthly-upgrade.yml
```

Then check it:

```bash
sleep 5  # let the run register
gh run list --workflow=monthly-upgrade.yml --limit 1
```

The workflow will:
1. Build both envs from the updated yamls on linux + mac.
2. Run `scripts/test_env.py --ci` on each.
3. If the main-list changed (add/remove) or any main-list package resolved
   to a new version, commit refreshed lockfiles and tag `YYYY.MM.<next>`,
   then publish a GitHub release.

### 6. Report back

After the run completes, tell the user:
- the new tag (`git fetch --tags && git tag --list '20*.*.*' --sort=-v:refname | head -1`)
- the release URL (`gh release view <tag> --json url -q .url`)
- any notable version bumps from the release notes

## Failure modes

- **Workflow run fails the smoke test**: a new/changed dep broke import.
  Read the failing job log (`gh run view <id> --log-failed`), decide whether
  to revert the commit or fix the yaml (often: pin to a known-good version,
  or swap for an alternative).
- **No new tag appears after a successful run**: nothing in the main list
  actually changed. For pure pin-tightening on a package that already
  resolves to the same version, this is expected and fine.
- **Removing a package that another consumer repo still imports**: the
  shared-env smoke test won't catch this. Warn the user when removing a
  package that they may need to add it back to a consumer repo's
  `pyproject.toml`.
- **Platform-specific package**: if a package is linux-only (CUDA-bound) or
  mac-only, edit just one yaml and call this out in the commit body.

## What this skill does NOT do

- Rebuild your local env. After a new tag is published, the user runs
  `make latest` themselves.
- Edit consumer-repo `pyproject.toml`s. Per the repo convention, when a dep
  is promoted to the shared env it should be removed from any consumer
  repos that previously listed it — but that's a separate, manual task.
- Edit lockfiles directly. CI owns those.
